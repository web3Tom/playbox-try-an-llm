# ADR-0001 (rev. 2026-05-28): Output & context limits for the `gpt-5.4` reasoning model in `kilo.json`

- **Status:** Accepted — revises the pre-confirmation draft after a live truncation incident
- **Date:** 2026-05-28
- **Deciders:** Playbox "Try an LLM" template lead
- **Context tags:** kilo-code, reasoning-models, model-routing, rate-limits

## Context

`gpt-5.4` is the Plan agent's reasoning model and is **confirmed to be a reasoning model**.
A live run hit Kilo Code's "model hit its output limit while reasoning and produced no
actionable output." Diagnosis revealed three *distinct* ceilings that had been conflated:

| Ceiling | Scope | Observed value | Role in the failure |
|---|---|---|---|
| **TPM** (tokens/minute) | Whole deployment, all users, per minute | 3,000,000 (max 4,000,000) | None — a throughput quota, not a per-response cap |
| **Context window** | Per request (input + output) | 128,000 (run was at 52%) | None — ample headroom remained |
| **`max_completion_tokens`** (per-request output) | Per request: **reasoning + visible output combined** | 16,384 | **Root cause** — reasoning consumed the entire budget before any answer |

Key fact: for a reasoning model, reasoning tokens are spent from the *same* per-request
output budget as the visible answer. 16,384 was fully absorbed by reasoning, leaving zero
for actionable output. Neither TPM nor context window governs this; only the per-request
output cap (and reasoning effort) does.

## Decision

1. **Raise the Plan agent's per-request output cap from 16,384 → 32,768**, contingent on the
   deployment's *per-request* max output supporting it (this is a different field from the
   3,000,000 TPM quota — verify on the Azure deployment).
2. **Keep the context window at 128,000.** It was not the constraint. Raise only if the
   deployment advertises a larger window (reasoning models often support 200K+), as a
   separate performance lever for holding more codebase — not a fix for truncation.
3. **Tune reasoning via variant per role.** High reasoning variant for planning only; medium/low (or
   off) for routine edits. The cap alone is not the lever — calibrated reasoning is.
4. **Treat the 3,000,000 TPM as a shared throughput budget managed via model routing**, not a
   per-response setting. At 100–150 peak users, heavy unrouted reasoning turns (~90K tokens
   each → ~33 req/min) can approach the quota; routing routine work to `gpt-5-mini`/`nano`
   keeps aggregate consumption comfortably under it.

### Per-role caps

| Role | Model | `output` cap | Reasoning variant |
|---|---|---|---|
| plan | `gpt-5.4` | 32,768 | High (planning only) |
| code | `gpt-5-mini` | 16,384 | Medium (default) |
| react-frontend | `gpt-5.2` | 16,384 | Medium; high for complex logic |
| summarizer | `gpt-5-nano` | 16,384 | Off / minimal |

```json
{
  "limit": { "context": 128000, "output": 32768 }
}
```

## Consequences

**Positive**

- Reasoning + actionable output both fit in one turn; no more "produced no actionable output."
- Three-ceilings distinction documented, preventing the TPM-vs-output confusion from recurring.
- Routing discipline now backed by a concrete capacity number.

**Negative / trade-offs**

- Higher worst-case per-turn cost and latency on the Plan agent (acceptable: low-frequency role).
- Larger per-request consumption draws harder on the shared 3M TPM — mitigated by routing.

**Follow-ups / guardrails**

- Confirm the deployment's **per-request max output** ≥ 32,768 before relying on the new value.
- Monitor 429 / rate-limit events at peak; if they appear, the lever is *routing*, not raising TPM.
- If the deployment advertises a context window > 128K, evaluate raising `context` separately.

## Update 2026-06-03: Agent Roster & Schema Refinement

The original ADR captured the reasoning model cost/capability design. Since then, the Kilo agent roster has been finalized:
- `orchestrator` → `plan` (Kilo built-in override in `kilo.jsonc`, gpt-5.4)
- `everyday-dev` → `code` (Kilo built-in override in `kilo.jsonc`, gpt-5-mini)
- New agents: `doc-writer` (gpt-5-mini), `react-frontend` (gpt-5.2, variant: high), `summarizer` (gpt-5-nano)
- Per-model capabilities now live in `provider.playbox-apim.models` catalog in `kilo.jsonc`
- `reasoningEffort` property removed → replaced by `variant` (named presets: high/medium/low)
- `fallback` property removed → explicit escalation via agent routing (e.g., react-frontend escalates to Plan agent for hard cases)
- Context windows: gpt-5.4/gpt-5.2 = 200,000; gpt-5-mini/nano = 128,000
- Output caps per agent above; gpt-5.4 reasoning route = 32,768; others = 16,384

The rationale and cost-control principles in the original decision remain unchanged.
