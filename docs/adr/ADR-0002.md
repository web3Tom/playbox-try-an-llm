# ADR-0002: Image-attachment capability per model and the OCR execution strategy

- **Status:** Accepted — pending live-deployment verification of image ingest (see Follow-ups)
- **Date:** 2026-06-04
- **Deciders:** Playbox "Try an LLM" template lead
- **Context tags:** kilo-code, vision, ocr, model-routing, model-catalog, cost-control
- **Relates to:** [ADR-0001](ADR-0001.md) (output & context limits) — this ADR reuses its three-ceilings model and routing discipline.

## Context

Two questions surfaced once the catalog gained image-capable routes (`gpt-5.4`, `gpt-5.2`):

1. **Which models should declare image-attachment capability, and does enabling it change their
   `limit.context` / `limit.output` settings?**
2. **How should OCR / document-parsing tasks be executed** — send everything to a vision model,
   extract text deterministically, or route between the two?

The catalog (`provider.playbox-apim.models` in `.kilo/kilo.jsonc`) currently declares:

| Model | `attachment` | `modalities.input` | `context` | `output` | Role |
|---|---|---|---|---|---|
| `gpt-5.4` | `true` | `["text","image"]` | 200,000 | 32,768 | plan |
| `gpt-5.2` | `true` | `["text","image"]` | 200,000 | 16,384 | react-frontend |
| `gpt-5-mini` | `false` | `["text"]` | 128,000 | 16,384 | code, doc-writer |
| `gpt-5-nano` | `false` | `["text"]` | 128,000 | 16,384 | summarizer |

### Key facts that drive the decision

- **`attachment` + `image` modality is a *capability* flag, not a *budget* setting.** It tells Kilo
  the route will accept image content. It does **not** change the deployment's context or output
  ceilings.
- **Images are billed against the *input* (context) budget, not the output budget.** A vision model
  tiles each image into tokens (a single high-resolution page can cost on the order of ~1,000+
  input tokens). So image attachment changes **how fast the context window fills**, never the
  output cap. Output remains text-only (`modalities.output: ["text"]`) and is unaffected by
  enabling image input.
- **Therefore the `limit.context` / `limit.output` numbers do not need to change *because* a model
  is image-capable.** They are deployment ceilings (per ADR-0001). What changes is the
  *operational fill discipline*: image-heavy prompts consume context faster, so the practical
  text headroom on a vision route is smaller than the raw 200,000 implies.
- **OCR on a text-only route is impossible by design.** `gpt-5-mini` / `gpt-5-nano` are
  `attachment: false`; they cannot receive image pixels, so any OCR work must route to a
  vision-capable model.
- **A PDF is an envelope, not a modality.** The catalog has no `pdf`/`document` modality. A
  born-digital PDF carries a selectable text layer (no vision needed); a scanned PDF is raster
  images (vision/OCR needed). Whether a given document needs the vision path is a **deterministic
  property of the file**, detectable in milliseconds — not a judgment call (cf. Rule 5: use the
  model for judgment, not deterministic transforms).

## Decision

### 1. Image-attachment capability is assigned by role need, not enabled blanket

| Model | Image-capable? | Rationale |
|---|---|---|
| `gpt-5.4` (plan) | **Yes** — keep | Planning may need to read architecture diagrams, screenshots, or spec images to reason about a task. |
| `gpt-5.2` (react-frontend) | **Yes** — keep; this is the **designated OCR/vision route** | Reads UI mockups/screenshots into components; vision-capable but cheaper than `gpt-5.4`, which stays reserved for planning. |
| `gpt-5-mini` (code, doc-writer) | **No** — stays text-only | Daily driver; vision adds cost and tokenizer overhead it does not need. OCR work routes to `gpt-5.2`. |
| `gpt-5-nano` (summarizer) | **No** — stays text-only | Cheapest, highest-frequency, read-only summarization; no image use-case. |

### 2. Image capability does **not** alter the limit settings

- `limit.context` and `limit.output` stay as set in ADR-0001 + the 200K refresh. Enabling
  `attachment` / `image` modality is orthogonal to those caps.
- **Operational rule (not a config change):** treat attached images as consuming input budget.
  Reserve headroom — apply the same 30–50% effective-fill discipline to *input after image
  tokens*, not to the raw context number. A 200,000 window with three full-page screenshots
  attached has materially less room for text+reasoning than an empty one.
- Do **not** raise `output` for vision routes. Image input has no bearing on the output budget;
  the only output-budget driver remains reasoning consumption (ADR-0001).

### 3. OCR tasks use a **hybrid detect-then-OCR router**, not all-model and not extraction-only

The chosen strategy is a two-stage pipeline that defaults to the cheap, exact path and reserves
the vision model for content that genuinely lacks a text layer:

| Stage | Action | Tool | Model? |
|---|---|---|---|
| **1. Detect** | Attempt text-layer extraction; measure yield | `markitdown` / `pdfplumber` (deterministic) | No |
| **2a. Text layer present** | Use the extracted text directly | same | No — free, fast, character-exact |
| **2b. Image-only / scanned** | Render page → image → OCR via vision | `pymupdf`/`pdf2image` to rasterize, then `gpt-5.2` image input | Yes — `gpt-5.2` only |
| **3. Structure (tables/forms)** | Transcribe layout to Markdown when the text layer loses structure | `gpt-5.2` vision | Yes — judgment task |

**Why hybrid (rejecting the two extremes):**

- **All-model (send every document to vision):** rejected. Burns the expensive image path on
  born-digital PDFs whose text is already perfectly extractable for free; worse accuracy than the
  native text layer (vision OCR can mis-read characters the text layer encodes exactly); higher
  latency and token cost; draws harder on the shared TPM (ADR-0001).
- **Extraction-only (never use vision):** rejected. Returns little or nothing on scanned/image-only
  PDFs and cannot read text embedded in screenshots, photos, stamps, or figures.
- **Hybrid:** routes on a deterministic file property (does a usable text layer exist?), so the
  *routing* is plain code and the *vision model* is spent only where it adds value. This is the
  Rule 5 boundary applied to documents.

### 4. Vision-language OCR vs. a dedicated OCR engine

`gpt-5.2` performs **vision-language OCR** — it reads text *in context* and can reason about it
(extract a total, transcribe a table to Markdown). It is **not** a substitute for a dedicated OCR
service (e.g. Azure Document Intelligence) when the task needs **bounding-box coordinates, dense
multi-column scans at scale, or per-character confidence scores**. For the Playbox's
"read-and-understand" demos, vision-LLM OCR is the right tool; high-volume coordinate-grade
digitization is explicitly out of scope for these routes.

## Consequences

**Positive**

- Image capability is justified per role; no blanket vision cost on the high-frequency cheap routes.
- The capability-vs-budget distinction is documented, preventing a future "we enabled images, do we
  need to raise the limits?" misfire (answer: no — adjust fill discipline, not caps).
- OCR cost is bounded: digital PDFs never touch the vision model; only genuine scans do.
- Single designated vision route (`gpt-5.2`) keeps `gpt-5.4` reserved for planning.

**Negative / trade-offs**

- The detect-then-OCR router is application code the demos must own (PDF cracking + rasterization
  are *not* done by the model — it accepts pixels, not a `.pdf`).
- Image-heavy prompts shrink effective text headroom on vision routes; users must be mindful of fill
  even with a 200K window.
- `gpt-5-mini` / `gpt-5-nano` cannot OCR at all; any demo needing OCR must route to `gpt-5.2`.

**Follow-ups / guardrails**

- **Verify the APIM gateway actually accepts image input** end-to-end on the `playbox-apim`
  provider at API version `2025-04-01-preview`. `attachment: true` is a *catalog declaration*; only
  a live image call proves the gateway passes image content through. (Same class of open
  verification as ADR-0001's per-request output cap.)
- **Confirm PDF→image rendering is available in the DevPod image** (`pymupdf` or `pdf2image` +
  poppler) before shipping any OCR demo that depends on stage 2b.
- If a high-volume / coordinate-grade OCR use-case appears, evaluate a dedicated OCR service rather
  than stretching `gpt-5.2`.
